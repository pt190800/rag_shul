01 רקע ומטרת הפרויקט

rag_shul הוא מערכת RAG (Retrieval-Augmented Generation) שנבנתה על גבי שולחן ערוך, אורח חיים — אחד מספרי ההלכה הבסיסיים ביהדות.

מה המערכת עושה?

המשתמש שואל שאלת הלכה בעברית. המערכת:

  1. מחפשת בשולחן ערוך את הקטעים הרלוונטיים ביותר לשאלה
  2. מעבירה אותם ל-GPT יחד עם השאלה
  3. GPT מייצר תשובה מבוססת-מקורות

בנוסף, ניתן להשוות תשובות עם ובלי RAG — כדי למדוד כמה ה-RAG מועיל.

הגרסיון של הטקסט

הטקסט מבוסס על מהדורת תורת אמת 363, כולל:

  • 697 סימנים
  • ~4,169 סעיפים
  • ~30,000 מילים
  • טקסט המחבר + הגה"ה של הרמ"א

07 תהליך 5 — הטמעת וקטורים (Embedder)

שלב 3 embedder/embed.py

ממיר כל צ'אנק טקסט לוקטור מספרי (Embedding) בגודל 1024 מספרים, ושומר הכל ב-ChromaDB — מסד נתונים וקטורי שמאפשר חיפוש מהיר.

קלט data/chunks_siman.json
פלט embedder/chroma_db/
12,500 וקטורים × 1024 מימדים

מה קורה בפנים?

צ'אנקים מה-JSON
↓
הוספת prefix: "passage: " + טקסט
↓ (למשל: "passage: סימן 1, סעיף 1: ישתדל אדם...")
מודל multilingual-e5-large (1024 מימדים)
↓ קידוד בקבוצות של 32
וקטור float32 מנורמל (L2-normalized)
↓
שמירה ב-ChromaDB

המודל: multilingual-e5-large

  • מודל שפה רב-לשוני של Microsoft / Hugging Face
  • מאומן על pairs של שאלות-תשובות
  • מייצר וקטורים של 1024 מימדים, מנורמלים (L2)
  • חובה: "passage: " לפני טקסט, "query: " לפני שאלה — ללא זה הביצועים יורדים משמעותית

הפונקציות הראשיות

build_encoding_texts(...)   → list[str]  # "passage: ..." לכל צ'אנק
embed(texts, model, ...)    → np.ndarray (N, 1024)
encode_query(query, ...)    → np.ndarray (1024,)
store_in_chroma(...)        → שמירה ל-ChromaDB
get_existing_type_texts()   → set  # כדי לא להטמיע שוב

08 תהליך 6 — שליפה (Retriever)

שלב 4 retrievers/chroma_retriever.py

מקבל שאלה, ממיר אותה לוקטור, ומחפש ב-ChromaDB את הצ'אנקים הקרובים ביותר מבחינה סמנטית.

קלט שאלה בעברית + top_k
פלט רשימה מדורגת: rank, score, text, siman, seif

מה קורה בפנים?

שאלה: "מה דין ציצית?"
↓
encode_query("query: מה דין ציצית?") ← prefix חשוב!
↓ וקטור (1024,)
ChromaDB: cosine similarity מול 12,500 וקטורים
(similarity = dot product כי הוקטורים מנורמלים)
↓
דירוג לפי ציון + החזרת top_k

שלושת ה-Retrievers בפרויקט

שימוש

from retrievers import get_retriever

# גרסה אחת
r = get_retriever("chroma", type_text="text+hagah")

# כל הגרסאות בנפרד

09 תהליך 7 — הערכה (Evaluation)

שלב 5 evaluation/retrieval_evaluator.py

בודק כמה טוב ה-Retriever — כמה פעמים הוא מוצא את הסימן הנכון ב-K התוצאות הראשונות.

קלט data/eval/sa_eval.csv
596 שאלות — עמודות: #, שאלה, תשובה, סימן, סעיף
פלט Recall@[1,3,5,10,18,30,50], MRR, elapsed_sec, target_passed

האלגוריתם

לכל שאלה מ-596:
↓ שליפת top_100 תוצאות (retrieve_k=100)
↓ מציאת דירוג הסימן הנכון
↓ Recall@K: האם הסימן נמצא בK הראשונים?
↓ MRR: 1/דירוג (או 0 אם לא נמצא)

בסוף: ממוצע על כל 596 השאלות

הסבר המדדים

Recall@K — כמה שאלות (באחוזים) הסימן הנכון שלהן נמצא בתוצאות K הראשונות (K נמדד ב-[1,3,5,10,18,30,50]):

  • Recall@1 = 59% — ב-6/10 שאלות, התוצאה הראשונה נכונה
  • Recall@3 = 79% — ב-8/10 שאלות, אחת מ-3 הראשונות נכונה
  • Recall@5 = 94% — ב-9.4/10 שאלות, אחת מ-5 הראשונות נכונה

MRR (Mean Reciprocal Rank) — ממוצע של 1/דירוג. MRR=0.686 פירושו שהדירוג הממוצע של התשובה הנכונה הוא ~1.46 — כמעט ראשון.

Granularity: המערכת סופרת לפי סימן, לא סעיף — כי שאלה יכולה להיות רלוונטית למספר סעיפים באותו סימן.

13 ביקורת הקוד — מה לא טוב ועצות לשיפור

פרק זה מציג ניתוח ביקורתי של הקוד כפי שהוא היום, מה לא עובד טוב, ועצות לשיפור.

13.1 ארכיטקטורה ועקביות

⚠️ שלושה Retrievers, שניים מהם מתים

יש שלושה מימושי Retriever בקוד: ChromaRetriever (פעיל ומומלץ), NpyRetriever (Legacy, נתיבים קשיחים), ו-SemanticE5SeifV6CombinedRetriever (Legacy, לא מתוחזק). הקוד הישן לא נמחק — מי שיבוא לפרויקט לא יודע מה לבחור.

עצה: מחק את npy_retriever.py ו-semantic_e5_seif_v6_combined.py, או העבר ל-retrievers/legacy/ עם הערה ברורה.
⚠️ experiments/exp_main.py ו-main.py זהים לחלוטין

שני הקבצים מכילים בדיוק את אותו קוד: load config → build_tables → embed. לא ברור מי "האמיתי" — שכפול מסוכן כי שינויים באחד לא ישתקפו בשני.

עצה: מחק את experiments/exp_main.py והשאר רק main.py בשורש כנקודת כניסה יחידה.
⚠️ main.py בשורש הפרויקט — מיותר

הקובץ הוא "Legacy RAG query loop template" ולא משמש לכלום בפועל — ה-UI וה-evaluator הם נקודות הכניסה האמיתיות.

עצה: מחק אותו, או הפוך אותו ל-CLI שימושי אמיתי.

13.2 ניהול תצורה (Configuration)

⚠️ נתיבים קשיחים בכמה מקומות

15 הוספת Retriever חדש

המערכת בנויה כך שניתן להוסיף Retriever חדש בשלושה צעדים.

שלב 1 — צור את הקלאס

# retrievers/my_retriever.py
from .base import BaseRetriever
import numpy as np
from pathlib import Path
from sentence_transformers import SentenceTransformer

class MyRetriever(BaseRetriever):
    @property
    def name(self) -> str:
        return "my_retriever"

    def __init__(self, **_ignored):
        self._model = self._embeddings = self._chunks = None

    def _load(self):
        if self._model:
            return
        self._model = SentenceTransformer("intfloat/multilingual-e5-large")
        base = Path(__file__).resolve().parent.parent
        self._embeddings = np.load(str(base / "MY_EMBEDDINGS.npy"))
        import json
        with open(base / "MY_CHUNKS.json", encoding="utf-8") as f:
            self._chunks = json.load(f)

    def retrieve(self, query: str, top_k: int = 10) -> list[dict]:
        self._load()
        qvec = self._model.encode("query: " + query, normalize_embeddings=True)
        scores = self._embeddings @ qvec
        top_idx = np.argsort(scores)[-top_k:][::-1]
        return [
            {
                "rank": r + 1,
                "chunk_id": self._chunks[i].get("chunk_id", i),
                "score": round(float(scores[i]), 4),
                "text": self._chunks[i]["text"],
                "siman_parent": self._chunks[i].get("siman", 0),
                "siman": self._chunks[i].get("siman", 0),
                "seif": self._chunks[i].get("seif", 0),
            }
            for r, i in enumerate(top_idx)
        ]

17 מודל E5 — למה דווקא הוא?

השוואת מודלים שנוסו

מודלR@3הסיבה לכישלון
E5-small34%קטן מדי (118M פרמטרים)
mBERT12%אינו sentence encoder — ארכיטקטורה לא מתאימה לדמיון
heBERT35%ספציפי לעברית אבל גם אינו sentence encoder
DictaBERT35%אותה בעיה כמו heBERT
BGE-large-en62%אנגלית בלבד — תרגום מאבד ניואנס הלכתי
E5-large ★80%Multilingual sentence encoder, 1024 מימדים, cross-lingual alignment

מה מיוחד ב-E5?

E5 (Embeddings from bidirEctional Encoder representations) פותח על ידי Microsoft Research. הוא אומן על מיליארדי זוגות טקסט ב-100+ שפות בשיטת Contrastive Learning — המודל לומד לקרב וקטורים של passage ושאלה רלוונטיים, ולהרחיק אחרים.

הסבר ה-prefix החובה

# ✅ נכון:
model.encode("passage: " + seif_text)   # לטקסטים
model.encode("query: "   + question)    # לשאלות

# ❌ שגוי — ביצועים יורדים משמעותית:
model.encode(seif_text)
model.encode(question)

E5 אומן עם ה-prefix הזה — הוא מסמן למודל אם הטקסט הוא "מסמך לחיפוש" או "שאלה שחיפשים". ללא ה-prefix, ה-alignment נשבר.

נורמליזציה וחיפוש מהיר

model.encode(..., normalize_embeddings=True)
# → וקטור L2-normalized (אורך 1)
# → cosine similarity = dot product
# → ניתן לחשב: scores = embeddings @ query_vec  (מטריצה × וקטור)
